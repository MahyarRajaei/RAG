# تصمیمات فنی

## ۱. انتخاب پایگاه داده

انتخاب پایگاه داده یکی از مهم‌ترین تصمیمات طراحی بود، چون سامانه باید همزمان دو نوع داده را نگهداری کند: فراداده‌ها (metadata) و بردارهای embedding.

نیاز مهم دیگر، حذف داکیومنت است. با حذف یک داکیومنت، تمام chunkهای مربوط به آن نیز باید حذف شوند. اگر از یک پایگاه داده برداری مانند ChromaDB برای embeddingها و یک پایگاه داده رابطه‌ای برای metadata استفاده شود، این حذف باید به صورت دستی و در دو سیستم جداگانه انجام شود. در این حالت خطر ناسازگاری داده‌ها وجود دارد؛ مثلاً ممکن است داکیومنت حذف شود ولی chunkهایش در پایگاه برداری باقی بماند.

به همین دلیل **PostgreSQL به همراه افزونه pgvector** انتخاب شد. با این انتخاب، metadata و بردارهای embedding در یک پایگاه داده و در قالب جدول‌های مرتبط نگهداری می‌شوند. با تعریف کلید خارجی همراه با `ON DELETE CASCADE`، حذف یک داکیومنت به صورت خودکار chunkهای آن را هم حذف می‌کند و یکپارچگی (integrity) داده‌ها بدون کد اضافه حفظ می‌شود. همچنین نیازی به نگهداری و هماهنگ‌سازی دو سیستم ذخیره‌سازی نیست.

## ۲. معماری لایه‌ای

سامانه به صورت لایه‌ای پیاده‌سازی شده تا اصل تفکیک مسئولیت‌ها (Separation of Concerns) رعایت شود. کد در لایه‌های مجزا سازمان‌دهی شده است:

- **application:** لایه API و مسیرها (route)
- **service:** منطق کسب‌وکار
- **repository:** دسترسی به داده و ارتباط با پایگاه داده
- **model:** مدل‌های داده
- **rag:** منطق مربوط به chunking و استخراج embedding

هر لایه فقط با لایه‌ی مجاور خود ارتباط دارد، بنابراین تغییر در یک بخش (مثلاً تغییر روش chunking یا پایگاه داده) روی بقیه‌ی بخش‌ها اثر نمی‌گذارد و تست کردن هر لایه به صورت مستقل ساده‌تر می‌شود.

## ۳. بارگذاری داکیومنت‌ها

فرایند بارگذاری داکیومنت توسط کاربر یکی از بخش‌های حساس طراحی است. استخراج متن، chunking و محاسبه‌ی embedding زمان‌بر هستند و اگر در همان چرخه‌ی درخواست انجام شوند، درخواست کاربر بلوکه می‌شود.

برای حل این مسئله چند رویکرد وجود دارد. رویکرد کامل‌تر، ایجاد یک صف با Redis و اجرای کارها توسط workerهای RQ است که پردازش داکیومنت‌ها را به ترتیب و مستقل از سرور API انجام می‌دهند. اما این رویکرد به زیرساخت و سرویس اضافه نیاز دارد.

در پیاده‌سازی فعلی، برای سادگی از **Background Tasks در FastAPI** استفاده شده است. API پس از دریافت فایل و ثبت آن، بلافاصله پاسخ می‌دهد و پردازش سنگین در پس‌زمینه انجام می‌شود. با این کار درخواست‌ها بلوکه نمی‌شوند. البته این روش محدودیت‌هایی دارد: کارها در همان پروسه‌ی سرور اجرا می‌شوند و اگر سرور در حین پردازش ری‌استارت شود، کار از بین می‌رود. در صورت رشد سامانه، می‌توان بدون تغییر در لایه‌ی service به Redis و RQ مهاجرت کرد.

## ۴. جلوگیری از ذخیره‌ی تکراری فایل‌ها

برای جلوگیری از ذخیره‌ی مجدد یک فایل یکسان، هش (hash) محتوای فایل محاسبه می‌شود. اگر فایلی با همان هش قبلاً وجود داشته باشد، پردازش تکرار نمی‌شود و شناسه (id) همان فایل موجود برگردانده می‌شود.

این روش در حالت همزمانی (race condition) به تنهایی کافی نیست. اگر دو فایل یکسان به طور همزمان آپلود شوند، هر دو درخواست متد `get_by_hash` را فراخوانی می‌کنند، هر دو نتیجه می‌گیرند که چنین فایلی وجود ندارد و در نتیجه دو رکورد ایجاد می‌شود. برای حل این مشکل، روی ستون هش یک **قید یکتایی (UNIQUE constraint)** در پایگاه داده تعریف شده است. به این ترتیب پایگاه داده خودش تضمین می‌کند که فقط یکی از درخواست‌ها موفق شود. درخواست دوم با خطای `IntegrityError` روبه‌رو می‌شود، این خطا مدیریت می‌شود و id فایل ثبت‌شده برگردانده می‌شود.

## ۵. استقرار و راه‌اندازی

کل سامانه با **Docker Compose** اجرا می‌شود و شامل دو سرویس است: سرویس API (FastAPI روی uvicorn) و سرویس پایگاه داده (تصویر `pgvector/pgvector:pg16`). چند تصمیم در این بخش اهمیت داشت:

- **مدیریت وابستگی‌ها با uv:** وابستگی‌ها از روی `uv.lock` و با گزینه‌ی `--frozen` نصب می‌شوند تا محیط اجرا کاملاً تکرارپذیر باشد. همچنین `pandoc` برای استخراج متن از انواع داکیومنت در ایمیج نصب شده است.
- **مسیر مطلق برای venv:** مسیر محیط مجازی در `PATH` باید مطلق (`/app/.venv/bin`) باشد، وگرنه runc نمی‌تواند `uvicorn` را پیدا کند و کانتینر اجرا نمی‌شود.
- **Healthcheck برای پایگاه داده:** سرویس API با شرط `service_healthy` منتظر آماده شدن Postgres می‌ماند. `depends_on` ساده فقط منتظر شروع کانتینر است، نه آماده بودن پایگاه داده، و این باعث خطای اتصال در زمان راه‌اندازی می‌شد.
- **Lifespan به جای `on_event`:** ساخت جدول‌ها (`init_db`) هنگام راه‌اندازی برنامه، به جای `@app.on_event("startup")` که منسوخ شده، در یک تابع `lifespan` انجام می‌شود.
- **مدیریت تنظیمات:** اطلاعات حساس مانند رمز پایگاه داده و کلیدهای API در فایل `.env` نگهداری و از طریق `env_file` به کانتینرها داده می‌شوند و داخل ایمیج یا مخزن کد قرار نمی‌گیرند.
